# AGENTS.md

Guidance for AI agents working in this repository.

## What this project is

`podman-pi-agent` is a container image project, not an application. It builds a minimal Ubuntu 26.04 image that runs the **pi coding agent** (`@earendil-works/pi-coding-agent`) and **pi-web** (`@jmfederico/pi-web`) with full `systemd` as the entrypoint. It is designed to run as a podman container, a Proxmox LXC container, or via podman quadlets.

## Repository layout

| Path | Purpose |
|---|---|
| `Dockerfile` | Image definition, **multi-stage** (Ubuntu 26.04, systemd entrypoint, Node/Rust toolchains, pi + pi-web via npm, Godot engine + export templates + official docs system-wide; the full version tag is embedded as the `org.opencontainers.image.version` OCI label). Stages: `base` → `rust` / `godot` / `apps` → `runtime` → `final` |
| `build.sh` | Resolves latest component versions, writes version `.txt` files, builds `pi-agent:latest` + a versioned tag (pi-web's version comes from the vendored tarball, not the npm registry) |
| `build_and_run.sh` | `build.sh` + `run_local.sh` |
| `run.sh` | Example run script (creates container, sets root password at runtime, copies SSH key, attaches) |
| `run_local.sh` | Runs `run.sh` against the locally built `pi-agent:latest` image |
| `migrate.sh` | One-shot migration of an existing home folder from the old `ubuntu` user layout to the `agent` layout (`./migrate.sh <home-folder> [--dry-run]`) |
| `systemd/*.service` | `pi-web.service`, `pi-web-sessiond.service`, `pi-home-init.service` (seed an empty `/home/agent` mount from `/opt/agent-home-skeleton`) |
| `systemd/pi-web-restart.{service,timer}` | Daily 06:00 (container local time) restart of `pi-web-sessiond` then `pi-web` — temporary upstream workaround, `Persistent=true` so a missed slot runs at boot |
| `etc/pi-web/config.js` | pi-web gateway config, copied to `/etc/pi-web/config.js` |
| `etc/pi-agent/home/` | Per-home pi config stub (godot `SKILL.md`, `export_presets.cfg.example`) ingested into `/home/agent` on every boot by `init-agent.sh`; copied to `/etc/pi-agent/home/` |
| `bin/init-agent.sh` | Home-seeding + per-boot config-ingest script run by `pi-home-init.service` (also symlinks the system-wide Godot export templates into the agent home) |
| `bin/godot-wrapper.sh` | Copied to `/usr/local/bin/godot`; auto-adds `--headless` when no display server is available (real binary at `/usr/local/lib/godot/godot`) so headless CLI usage works |
| `node_version.txt`, `pi_version.txt`, `pi_web_version.txt`, `rust_version.txt`, `godot_version.txt`, `pi_agent_tag.txt` | Generated by `build.sh` (gitignored); the tag file is used by CI to detect build skips |
| `.github/workflows/docker-image.yml` | GitHub Actions workflow (see below) |

## GitHub Actions workflow

`.github/workflows/docker-image.yml` builds and pushes the image to `ghcr.io` on:
- push to `master`
- daily cron (06:00 UTC)
- manual dispatch (with optional `force` input)

It runs `CT_TOOL=docker ./build.sh --build-ghcr` (adding `--force` when dispatched with force). `--build-ghcr` skips the build entirely if the resolved version tag already exists on ghcr.io, and signals the skip by **deleting `pi_agent_tag.txt`**; the login/push steps then silently skip. Never re-push a same-tag image with different content — that's the invariant this check protects.

## Building

```bash
./build.sh            # podman if available, else docker; CT_TOOL env var overrides
./build_and_run.sh    # build + local run
```

`build.sh` fetches the latest stable Node major, pi, Rust and Godot versions from their upstreams, writes them to the version `.txt` files, and builds with those as build args. **pi-web is the exception:** its version is read from the vendored tarball `vendor/pi-web/jmfederico-pi-web-1.202610.1.tgz` (fork branch `fix/terminal-requested-terminal-reload-once` of `Gerporgl/pi-web`, which fixes the terminal list polling storm / "terminal URL spam") after a sha256 check; the `apps` stage installs that tarball with `npm install -g <tgz> --allow-scripts=node-pty` and asserts both the tarball version and the presence of `requestedTerminalReloadKey` in the installed terminal plugin. To refresh the fork build: re-pack upstream (`npm pack` runs `prepack`, so `dist/` is included — a `github:` install would ship no `dist/`), then update filename, both hashes, the `COPY` line and the `PI_WEB_VERSION` default **together**; never hotpatch the installed `dist/` (the plugin package revision is a whole-package sha256 checked by gateway and sessiond, so a patched file makes `/api/plugins` return 500). Revert to the registry install and delete `vendor/` once the fix is published upstream. Image tag format: `node-<major>-pi-<ver>-pi-web-<ver>-rust-<ver>-godot-<ver>`. The full tag is also embedded in the image as the `org.opencontainers.image.version` OCI label (overriding the base image's `26.04`), so it can be read at runtime via `podman inspect`.

### Multi-stage layout and cache rules (important when editing the Dockerfile)

Each component is its own stage and declares **only** the build args it consumes.
**Each stage is built separately (`--target <stage>`) and tagged `pi-agent-<stage>:latest`**,
and downstream stages refer to those *images* (`FROM pi-agent-base:latest`,
`COPY --from=pi-agent-rust:latest`) rather than the in-file stage names — same
pattern as `~/llama-lxc`. Intermediate stages therefore survive
`podman image prune` as real tagged images instead of becoming untagged layers.

| Stage → tag | Contents | Args declared |
|---|---|---|
| `base` → `pi-agent-base:latest` | apt layer, `agent` user setup, Node.js (NodeSource, apt) | `NODE_MAJOR` |
| `rust` → `pi-agent-rust:latest` | Rust toolchain + musl std | `RUST_VERSION`, `TARGET_ARCH` |
| `godot` → `pi-agent-godot:latest` | engine, wrapper, export templates, official docs | `GODOT_VERSION`, `TARGET_ARCH` |
| `apps` → `pi-agent-apps:latest` | pi (npm) + pi-web (from `vendor/pi-web/*.tgz`) npm installs (esbuild/relays pruning) + `/etc/pi-agent/npm-bins.tsv` generation | `PI_VERSION`, `PI_WEB_VERSION`, `TARGET_ARCH` |
| `runtime` → `pi-agent-runtime:latest` | assembly (`FROM pi-agent-godot:latest` + `COPY --from=pi-agent-rust:latest` then `pi-agent-apps:latest`) | none |
| `final` → `pi-agent:latest` + version tag | systemd units, `/etc/pi-web`, `/etc/pi-agent/home`, OCI label | `IMAGE_VERSION` |
| `vendor/pi-web/` | **Vendored pi-web tarball** (fork build, terminal polling fix); installed by the `apps` stage, version + sha256 verified by `build.sh` |
Keep these invariants when changing it:

- **Every stage keeps its `pi-agent-<stage>:latest` tag** (in both the Dockerfile `FROM`/`COPY --from=` lines and `build.sh`'s `build_stage` calls); short unprefixed names fail under podman (`short-name ... did not resolve to an alias`).
- **Never declare a version `ARG` globally.** podman/buildah busts *every* layer of a stage when any arg declared in that stage changes, even unused ones and layers above it; a global `IMAGE_VERSION`/`PI_VERSION` at the top makes every build a full rebuild.
- **Layer caching is linear**: in `runtime`, `COPY --from:` the rare components first (`rust`) and the frequent ones last (`apps`). In `final`, keep the ever-changing `LABEL` in that stage only.
- **`COPY` dereferences symlinks.** The npm global bin links (`pi`, `pi-web`) are re-created in `runtime` from `/etc/pi-agent/npm-bins.tsv` generated in the `apps` stage, and the root export-templates symlink is re-created too — do not try to `COPY` them.
- Node.js is installed by apt inside `base` (not copied between stages) so the final image's dpkg database stays consistent; a Node major bump therefore does rebuild everything (rare by design).
- `runtime` smoke-tests the assembled toolchain (`godot`, `rustc`, `cargo`, `node`, `npm`, `pi`, `pi-web`); keep it if you add stages.

**Podman is available on this machine** and is the preferred tool for building and running locally.

## Running and testing

- `./run.sh` is an example, not a requirement — the container is just a systemd-based Ubuntu box.
- Persistence: bind-mount your state at `/home/agent` (e.g. `-v ./home-data:/home/agent`). If the mount is empty, `pi-home-init.service` seeds it with a home skeleton; put your own `~/.pi/agent/models.json` and other pi configs in the mounted volume.
- Ports: pi-web UI on `8504`, SSH (for root admin access) on `2223`.

### Testing with your own scripts

The container's default entrypoint is **full systemd** (`/sbin/init`). To test by bind-mounting your own scripts, you must **override the entrypoint**, e.g.:

```bash
podman run --rm -it \
  --entrypoint /bin/bash \
  -v ./my-script.sh:/tmp/my-script.sh \
  pi-agent:latest \
  /tmp/my-script.sh
```

With the default entrypoint you get a booted systemd system (log in as root if a password was set); with an overridden entrypoint systemd does not run, which is fine for quick script/container testing.

## Conventions

- **Always confirm with the user before committing to git or pushing.** Never commit/push without explicit user approval.
- **After completing a task, update `README.md` and `AGENTS.md`** to reflect any changes (new scripts, options, ports, behaviors).
- The root password is intentionally not baked into the image; `run.sh` sets it at runtime. Without it, there is no way in — that is the intended secure default.
- Heavy tools (Godot binary, export templates, official Godot docs) live in system-wide image layers; `init-agent.sh` only ingests the small per-home config (the godot skill files and the export-templates symlink) on every boot, idempotently and without downloads. The godot skill files (`SKILL.md`, `export_presets.cfg.example`) are system-managed and **always synced** from the image on every boot (only rewritten when content differs) so image upgrades reach pre-existing home volumes — customise in a separate skill folder instead of editing them in place. Never bake per-user state into the home skeleton if it must reach pre-existing home volumes on upgrades — use the ingest path instead.
- No automatic apt updates inside the image (update timers removed); update by rebuilding.
- `ripgrep` and `fd-find` are installed in the `base` apt layer because pi's `grep`/`find` tools resolve their binaries as: `~/.pi/agent/bin/<name>` → `rg` / `fd`|`fdfind` on `PATH` → download from GitHub. Keeping both in apt means no runtime download and the image works offline (`PI_OFFLINE`). Do not remove them; a stale `~/.pi/agent/bin/fd` in a pre-existing home volume shadows the apt one (bin dir is checked first) and must be deleted manually.
- **No Godot MCP server in the image.** The `godot-mcp` npm package, its `mcp` stage / `GODOT_MCP_VERSION` arg and the default `etc/pi-agent/home/.pi/agent/mcp.json` were removed on purpose: Godot projects are created/edited as plain text files and run with bash + `godot --headless`, validated against the local docs at `/usr/local/share/godot-docs` (see the godot `SKILL.md`). Do not re-add a Godot MCP server. `init-agent.sh` ingests no `mcp.json` anymore — a user's own `~/.pi/agent/mcp.json` is never touched.
- `pi-web-restart.timer` (06:00 container local time) is a **temporary** workaround for upstream pi-web bugs (terminal URL spam, MCP server instantiation). It uses no hardcoded timezone: the container's local time comes from the host-mounted `/etc/localtime` (UTC otherwise). Delete `systemd/pi-web-restart.service`, `systemd/pi-web-restart.timer`, their `COPY` line and the `pi-web-restart.timer` entry in the `systemctl enable` line once upstream is fixed. The vendored pi-web tarball addresses the terminal URL spam, but keep the timer for now: remove it as its own commit only after the fixed build has been observed in a real deployment. (The "MCP instantiation" half of the rationale was mostly the since-removed Godot MCP server; the timer is still kept for the terminal-side bug.)
- `home-data/` and the version `.txt` files are gitignored (see `.gitignore`). `push.sh` is also intentionally ignored: it is a local helper script (run on another machine to push the built image to the local registry `registry.asqw.net`, tagging both `latest` and the version tag from `pi_agent_tag.txt`) that must never be committed. Options: `--dry-run`, `--keep-tags`; it refuses to run when `pi_agent_tag.txt` is missing or empty, which is also how a `--build-ghcr` skip (no new build) is detected.
- `vendor/pi-web/` is **not** gitignored and must not be added to `.dockerignore`: the 3.3 MB tarball is a build *input* committed so local builds and the GitHub Actions build get the same patched pi-web.
