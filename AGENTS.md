# AGENTS.md

Guidance for AI agents working in this repository.

## What this project is

`podman-pi-agent` is a container image project, not an application: a minimal Ubuntu 26.04 image running the **pi coding agent** (`@earendil-works/pi-coding-agent`) and **pi-web** (`@jmfederico/pi-web`) under full `systemd`. Runs as a podman container, a Proxmox LXC, or via quadlets.

## Repository layout

| Path | Purpose |
|---|---|
| `Dockerfile` | Multi-stage image definition: `base` → `rust` / `godot` → `playwright` → `apps` → `runtime` → `final` |
| `build.sh` | Resolves latest component versions, writes version `.txt` files, builds each stage as `pi-agent-<stage>:latest` plus `pi-agent:latest` and the version tag |
| `build_and_run.sh`, `run_local.sh`, `run.sh` | Build + example run (sets root password at runtime, copies ssh key, attaches) |
| `migrate.sh` | One-shot migration of an old `ubuntu` home folder to the `agent` layout (`./migrate.sh <home> [--dry-run]`) |
| `systemd/*.service` | `pi-web.service`, `pi-web-sessiond.service`, `pi-home-init.service` (seed empty `/home/agent` from `/opt/agent-home-skeleton`, then ingest config every boot) |
| `etc/pi-web/config.js` | pi-web config (JSON) → read-only `/etc/pi-web/config.js`, `PI_WEB_CONFIG` for gateway **and** sessiond |
| `etc/pi-agent/home/` | Per-home pi config stub (the system-managed skill folders: godot, playwright) ingested into `/home/agent` on boot → `/etc/pi-agent/home/` |
| `bin/init-agent.sh` | Home seeding + per-boot ingest, run by `pi-home-init.service` |
| `bin/godot-wrapper.sh` | `/usr/local/bin/godot`: adds `--headless` when there is no display (real binary at `/usr/local/lib/godot/godot`) |
| `bin/playwright-link.sh` | `/usr/local/bin/playwright-link`: symlinks the global `playwright` / `@playwright/test` into a project's `node_modules` (ESM/test-runner resolution without an npm install) |
| `bin/playwright-smoke.js` | Build-time smoke test run as `agent` in `runtime`: launches both installed browsers headlessly |
| `*_version.txt`, `pi_agent_tag.txt` | Generated by `build.sh` (gitignored); the tag file is how CI detects a build skip |
| `.github/workflows/docker-image.yml` | GitHub Actions build/push (see below) |

## GitHub Actions

Builds and pushes to `ghcr.io` on push to `master`, daily cron (06:00 UTC) and manual dispatch (`force` input). It runs `CT_TOOL=docker ./build.sh --build-ghcr` (`--force` when dispatched with force): the build is skipped when the resolved tag already exists on ghcr.io, signalled by **deleting `pi_agent_tag.txt`**, which makes the login/push steps skip. Never re-push a same-tag image with different content — that is the invariant this protects.

## Building

```bash
./build.sh            # podman if available, else docker; CT_TOOL env var overrides
./build_and_run.sh    # build + local run
```

Tag format: `node-<major>-pi-<ver>-pi-web-<ver>-rust-<ver>-godot-<ver>-pw-<ver>`; the same string is the `org.opencontainers.image.version` OCI label, readable with `podman image inspect`. Every component version belongs in the tag, otherwise a bump would re-push a same-tag image with different content. Never hotpatch the installed pi-web `dist/` in a running container (the plugin package revision is a whole-package sha256 checked by gateway and sessiond, so a patched file makes `/api/plugins` return 500) — bump the registry version and rebuild.

### Dockerfile cache rules (read before editing it)

Each component is its own stage declaring **only** the args it consumes; each stage is built separately (`--target <stage>`) and tagged `pi-agent-<stage>:latest`, and downstream stages refer to those *images* (`FROM pi-agent-base:latest`, `COPY --from=pi-agent-rust:latest`) — that is what keeps intermediate layers alive through `podman image prune`. Keep these invariants:

- **Every stage keeps its `pi-agent-<stage>:latest` tag** in both the Dockerfile `FROM`/`COPY --from=` lines and `build.sh`'s `build_stage` calls; short unprefixed names fail under podman.
- **Never declare a version `ARG` globally** — an arg declared in a stage busts every layer of that stage, even above it and even if unused.
- **Layer caching is linear**: in `runtime` copy the rare components first (`rust`), the frequent ones last (`apps`); keep the ever-changing `LABEL` in `final` only.
- **`COPY` dereferences symlinks**: the npm bin links (`pi`, `pi-web`) are re-created in `runtime` from `/etc/pi-agent/npm-bins.tsv` (generated in `apps`), and so is the root export-templates symlink. `playwright`'s link is created in the `playwright` stage and inherited by `runtime`, so it needs no re-creation.
- **`playwright` is built `FROM pi-agent-godot:latest` and `runtime` is `FROM pi-agent-playwright:latest`**: browser system libraries come from `playwright install --with-deps`, and apt packages cannot be `COPY`ed between stages, so the stage that installs them must sit in the assembly's base chain. Keep the `playwright-link.sh` `COPY` *after* the browser `RUN` so editing the helper never costs a browser re-download.
- `ENV` in the `playwright` stage (`PLAYWRIGHT_BROWSERS_PATH`, `NODE_PATH`) reaches the image config only — see the pi-web gotcha below.
- Node.js is apt-installed inside `base` so dpkg stays consistent; a Node major bump rebuilds everything (rare by design).
- `runtime` smoke-tests the assembled toolchain (`godot`, `rustc`, `cargo`, `node`, `npm`, `pi`, `pi-web`, and `bin/playwright-smoke.js` as the `agent` user); keep that if you add stages.

**Podman is available on this machine** and is preferred for local builds and runs.

## Running and testing

- `./run.sh` is an example, not a requirement — the container is just a systemd-based Ubuntu box.
- Persistence: bind-mount `/home/agent` (e.g. `-v ./home-data:/home/agent`); put your own `~/.pi/agent/models.json` in that volume.
- Ports: pi-web UI `8504`, root-admin SSH `2223`.

To test with bind-mounted scripts, override the entrypoint (the default one is `/sbin/init`, so systemd does not run with an overridden entrypoint — fine for quick checks):

```bash
podman run --rm -it --entrypoint /bin/bash \
  -v ./my-script.sh:/tmp/my-script.sh pi-agent:latest /tmp/my-script.sh
```

Playwright check (browsers are image layers, so nothing is downloaded; `su -`
also proves PAM login shells carry `PLAYWRIGHT_BROWSERS_PATH` / `NODE_PATH`):

```bash
podman run --rm --entrypoint bash -v ./bin/playwright-smoke.js:/tmp/smoke.js:Z \
  pi-agent:latest -c 'su - agent -c "node /tmp/smoke.js"'
```

## Conventions

- **Never commit or push without explicit user approval.**
- **After finishing a task, update `README.md` and `AGENTS.md`** (new scripts, options, ports, behaviors). Keep both short: this project is simple, so long prose and verbose comments make it look bigger than it is.
- No root password is baked in; `run.sh` sets it at runtime. Without it there is no way in — the intended secure default.
- Heavy tools (Godot binary, export templates, docs, Playwright browsers) are image layers; `init-agent.sh` only ingests the small per-home config on boot, idempotently and without downloads. It syncs **every** folder under `/etc/pi-agent/home/.pi/agent/skills/` (godot, playwright) — system-managed and **always synced** from the image (rewritten only when content differs) so upgrades reach pre-existing home volumes; customise in a separate skill folder instead. Never bake per-user state into the home skeleton when it must reach existing homes: use the ingest path.
- No automatic apt updates (timers removed); update by rebuilding.
- **pi-web feature toggles are baked, not user-editable**: `etc/pi-web/config.js` (JSON despite the `.js` name) becomes the read-only `/etc/pi-web/config.js`, and **both** units must set `PI_WEB_CONFIG` to it — session-daemon keys (`spawnSessions`, `subsessions`, `environmentFacts`, …) only take effect there, never in the gateway alone. The services run as `agent`, so the Settings screen cannot save to it: edit the repo file and rebuild. Session spawning and subsessions are off — they cost context a small local model cannot spare.
- Keep `ripgrep` + `fd-find` in the `base` apt layer: pi resolves its `grep`/`find` binaries as `~/.pi/agent/bin/<name>` → `rg` / `fd`|`fdfind` on PATH → GitHub download, so apt install means no runtime download and the image works offline (`PI_OFFLINE`). A stale `~/.pi/agent/bin/fd` in an existing home volume shadows the apt one and must be deleted manually.
- **No Godot MCP server in the image** — removed on purpose (`godot-mcp` package, its stage/arg and the default `mcp.json`). Godot work is plain text files + `godot --headless`, validated against `/usr/local/share/godot-docs`. Do not re-add it; `init-agent.sh` never touches a user's own `~/.pi/agent/mcp.json`.
- **Playwright stays system-wide and headless-only**: `playwright` + `@playwright/test` in one npm transaction (installed separately they fight over the `playwright` bin link, EEXIST; then `/usr/bin/playwright` is re-pointed at `@playwright/test/cli.js`, the superset CLI), browsers `chromium-headless-shell` + `firefox` only, installed by `playwright install --with-deps` into `/usr/local/share/ms-playwright` (read-only for `agent`; agents must never run `playwright install`). No full Chromium build and no WebKit — there is no display server in this image.
- **Env plumbing gotcha**: systemd services do *not* inherit the container image `ENV`, and PAM login shells (`ssh`, `su -`, `sudo`) start clean. So Playwright paths are declared in **three** places: image `ENV` (`podman exec`, direct runs), `/etc/environment` (PAM shells) and `Environment=` in `systemd/pi-web.service` + `pi-web-sessiond.service` (that is what reaches pi sessions). Adding a new service or global tool needs the same treatment.
- `npm link playwright` fails in this image (EPERM: npm chmods the read-only global install) — that is why `playwright-link` exists. `playwright-core` is *not* top-level: it lives at `/usr/lib/node_modules/playwright/node_modules/playwright-core` (also where the API `.d.ts` reference is).
- `home-data/`, the version `.txt` files and `push.sh` are gitignored. `push.sh` is a local helper (run on another machine to push the built image to `registry.asqw.net`, tagging `latest` and the version tag from `pi_agent_tag.txt`; options `--dry-run`, `--keep-tags`) and must never be committed; it refuses to run when `pi_agent_tag.txt` is missing or empty, which is also how a `--build-ghcr` skip is detected.
